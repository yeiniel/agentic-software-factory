# The Graph is versioned data interpreted by the core

How a Run proceeds is no longer written into the core. The Graph is the whole state and transition graph of a Task: its Activities, which run in parallel, the retry loops and their budgets, which failure retriggers whom with what Feedback, and the Task statuses and the transitions between them (running, done, Blocked). The core only interprets it; it knows two kinds of Activity, an agentic one that runs a named role and a deterministic one that runs a named script, and it does not know the names `implementor` or `acceptance-writer`. A new role is a new resource (ADR 0015) named in the Graph, with no change to the core. The model is a statechart in vocabulary (states, parallel regions, transitions on outcomes), as our own small JSON subset and not a standard's dependency. A loop is a built-in kind of state: it declares its attempts, and the core defines that the budget resets on entry and that a succeeded loop is kept; transitions leave it on an outcome or on exhaustion. The Graph describes one Task; the Factory runs one Run at a time (`docs/design.md`), so there is no cross-Task queue in it, and that is a known limit for when Tasks run in parallel. The Graph document is JSON and names its prose and scripts by relative path, so the Graph is a folder in the Factory repository: the state graph, the role instructions, system prompts and skills, the Activities' `run` scripts and the Feedback messages. This supersedes ADR 0015 on where those resources live and who owns them (the Graph, no longer the core); the core still writes them into each Run Context as ADR 0015 describes. A Feedback message may use only two placeholders, `{check}` and `{output}` (the failing Activity's raw output, truncated to the Factory's cap), so what a human writes there can never disclose the other Agent's branch. A Graph state maps onto a fixed set of Task statuses owned by the core, `running`, `done` and `blocked` plus a reason, so the Adapters and the Console do not change when the Graph does. There is no retry for a moved `main`: Tasks run in sequence and adding a Task writes to `refs/issues/*`, so only a human push could move it, and a refused fast-forward ends the Task `blocked` with reason `main-moved`. For the same reason `main` always equals `base` during a Task, so an Activity's Run Context names only `base` and branches as inputs and the Integrator no longer rebases onto a latest `main`; the Repo Host's `expect_main` guard stays. We chose this over keeping the graph as code because the Graph is what has changed most between experiments (ADR 0016 split a step and nested the loops, both by hand after a Run showed it was wrong), so it has to be cheap to edit, diffable and checkable, and because it keeps the work's order outside the Agents (ADR 0002).

The Graph is the same for every Task and the Factory ships a default; a per-repository override is later work. It lives in the Factory's own repository and its version is the commit it was loaded from. The Factory loads and checks it once, at start, and refuses to start on an invalid Graph; a changed Graph takes a restart. A Task pins the version at `task-received` and keeps it through its retries, so every result belongs to exactly one version and the Records say which. Only a human changes the Graph, through an ordinary commit; an Agent never sees it or edits it, and the Factory proposing candidate Graphs is later work. A Graph chooses steps and loops but cannot loosen what the core and the Adapters hold fixed: Agents only edit files, blindness by construction (ADR 0003), only the Factory advances `main`, Agent-written code runs only in containers (ADR 0012), and Agents reach only the model server (ADR 0019). A Task reaches `done` only through the publish Activity, a core effect that fast-forwards `main` (ADR 0004); the core rejects at load any Graph with another way into `done`.

## Considered Options

- The Graph as code, swapped as a whole implementation: simple, but every experiment edits the core and the graph cannot be checked or diffed apart from the machinery that runs it.
- A Graph per repository from the start: projects clearly differ (a Python library and a pnpm monorepo), but there is no evidence yet of what they would need.
- The Factory changing its own Graph: no signal yet to trust, and no fixed set of Tasks to measure a change against.

## Consequences

- The retry and blame rules in `src/factory/run.py` (the role constants, the two loop functions, the rule that a failed integration retriggers only the Implementor, and the Run cap) move into the default Graph. ADR 0016's loops and defaults stay as that Graph's content, and the config's attempt budgets become Graph fields.
- For now this makes the Graph editable. Deciding when a changed Graph is better is left open; what is documented first is a set of baseline scenarios: the Tasks already run (`pydantic-extra-types` #326, `tailwind-merge`, `unjs/ufo` #379), each with the end state the default Graph must give it, done or not.
- `docs/design.md` and the glossary's **Run** entry still describe today's default Graph as if it were the only one, and are updated when the interpreter is specified.
